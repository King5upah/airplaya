# Mirroring over the cable

AirPlay is not the only way an iPhone will hand over its screen. Plugged in, it
exposes a second protocol — the one QuickTime Player on a Mac uses when you pick
an iPhone as a recording source. It has nothing in common with AirPlay: no
discovery, no pairing, no FairPlay, no encryption, no network. This document
covers what it is, how `airplaya` speaks it, and where the Windows-specific
trouble lives.

If you have read [`airplay.md`](airplay.md), the contrast is the point. Over
Wi-Fi the phone is the client and we are the television; over the cable we are
the host and the phone is a capture device.

| | Wi-Fi (AirPlay v1) | Cable (QuickTime capture) |
|---|---|---|
| discovery | mDNS `_airplay._tcp` | USB enumeration |
| who connects | the phone connects to us | we open the phone's endpoints |
| authentication | legacy pairing, Ed25519 + X25519 | none |
| content protection | FairPlay, then AES-128 | none |
| video | H.264 in AES-CTR, ~30 fps | H.264 in the clear, up to 60 fps |
| audio | AAC-ELD 44.1 kHz | LPCM 48 kHz, already decoded |
| latency | network dependent, 100–200 ms | ~40 ms |
| the phone's UI | "Screen Mirroring" in Control Centre | nothing; it just starts |

The tradeoff is the cable itself, plus a driver prerequisite on Windows that is
the reason most tools do not offer this.

---

## 1. The hidden USB configuration

A USB device can describe several *configurations*, and only one is active at a
time. An iPhone normally shows one:

```
configuration 1
  interface 0   class 0xFF (vendor), subclass 0xFE   2 bulk endpoints
```

That is the `usbmuxd` pipe — the multiplexed channel Xcode, Finder and iTunes
use for everything from installing apps to reading crash logs.

A vendor control request unlocks a second one:

```
bmRequestType 0x40   (host to device, vendor, device recipient)
bRequest      0x52
wValue        0x0000
wIndex        0x0002   (0x0000 turns it back off)
no data stage
```

The phone answers by *disconnecting*. A second or two later it comes back
describing two configurations:

```
configuration 1
  interface 0   vendor, subclass 0xFE   usbmux            2 bulk endpoints
configuration N
  interface 0   vendor, subclass 0xFE   usbmux            2 bulk endpoints
  interface 1   vendor, subclass 0x2A   screen capture    2 bulk endpoints
```

Subclass `0x2A` is the one we want. Selecting configuration N and claiming that
interface gives a bulk IN endpoint carrying media and a bulk OUT endpoint for
our replies. `usbmux` stays available on the same configuration, so the phone
does not vanish from Finder while mirroring.

The control request usually fails with an I/O error *because* the device
disconnects before it can acknowledge — that failure means it worked.
`activate()` ignores the error and polls for the new descriptor instead.

### Endpoint hygiene

A session that ended badly can leave an endpoint halted, and a halted bulk
endpoint does not fail — it simply never delivers anything. Both endpoints get a
`CLEAR_FEATURE(ENDPOINT_HALT)` before the first read:

```
bmRequestType 0x02   bRequest 0x01   wValue 0   wIndex <endpoint address>
```

### Putting it back

Leaving the AV configuration selected confuses some versions of iTunes, which
expect configuration 1. `deactivate()` sends the request with `wIndex = 0` and
selects the usbmux configuration again on the way out.

## 2. Framing

Every transfer on the AV endpoints is a stream of length-prefixed frames:

```
offset  size  meaning
0       4     total length, little-endian, including these 4 bytes
4       4     packet magic
8       ...   the rest
```

Bulk reads do not respect frame boundaries — one read can return two frames and
half of a third — so the reader buffers and only emits whole frames. Everything
downstream sees the frame with the length stripped, which is why the parsers in
`packets.py` start at the magic.

**Magics are little-endian.** `ping` appears in a hex dump as `67 6e 69 70`,
which reads as `gnip`. Every constant in the code is written in reading order
and reversed on the wire, because getting this backwards produces parsers that
look right and match nothing.

Three packet types:

| magic | meaning |
|---|---|
| `ping` | keepalive; send back an identical one |
| `sync` | a request that must be answered with an `rply` |
| `asyn` | an unsolicited message, in either direction. The media is here |

A `sync` or `asyn` names the clock it concerns:

```
sync:  magic(4) clockRef(8) subtype(4) correlationID(8) payload...
asyn:  magic(4) clockRef(8) subtype(4) payload...
rply:  magic(4) correlationID(8) padding(4) payload...
```

The correlation id is generated by the phone and must come back unchanged; it is
how the phone matches an answer to its question.

## 3. Clocks, which is most of the protocol

Nearly every `sync` exchange is about clocks. CoreMedia identifies each one with
an 8-byte `CFTypeID`, an opaque handle that means nothing to us except as
something to quote back. The phone hands us references to its clocks and asks us
for references to ours; afterwards it asks what time it is on ours, and paces
the stream from the answers.

We invent references by adding a constant to the phone's:

| ours | derivation |
|---|---|
| audio clock | device audio clock + `1000` |
| video clock | device video clock + `0x1000AF` |
| any other clock | the requested ref + `0x10000` |

The values are arbitrary — a Mac uses real CoreMedia handles — but they have to
be distinct and stable, and constant offsets make a packet capture readable.

`CMTime` is a 24-byte struct:

```
value  int64    the reading
scale  uint32   units per second, 1_000_000_000 for our clocks
flags  uint32   0x1 = has been rounded, which is what we send
epoch  int64    0
```

Readings must come from a **monotonic** clock. Wall-clock time can step
backwards, and a clock that goes backwards makes the phone stall.

### SKEW

`SYNC SKEW` asks how fast our audio clock runs compared with the phone's,
expressed in the phone's own timescale — equal rates give back `48000`. The
phone resamples based on the answer, so it is measured rather than hardcoded:
the elapsed time on our audio clock since the first audio sample, scaled into
the phone's timescale, divided by the phone's own elapsed time.

Answering a constant works until the two clocks drift, at which point the audio
slowly slides against the picture.

## 4. The handshake

Nothing arrives until this has run. In particular the phone sends no video at
all until it has received an `ASYN NEED`.

```
phone                                  airplaya
  PING                     ──────>
                           <──────     PING
  SYNC CWPA                ──────>     (its audio clock)
                           <──────     ASYN HPD1   start video, screen size
                           <──────     RPLY        our audio clock
                           <──────     ASYN HPA1   start audio, format
  SYNC AFMT                ──────>     (the audio format it will send)
                           <──────     RPLY        {"Error": 0}
  SYNC CVRP                ──────>     (its video clock + the video format)
                           <──────     ASYN NEED   send video
                           <──────     RPLY        our video clock
  ASYN SPRP ×2             ──────>     (properties; informational)
  SYNC CLOK                ──────>     make us a clock
                           <──────     RPLY        the new clock
  SYNC TIME ×2             ──────>     what time is it
                           <──────     RPLY        a CMTime reading
  SYNC SKEW / OG / STOP    ──────>     RPLY ...
  ASYN FEED                ──────>     one video frame
                           <──────     ASYN NEED   after every frame
  ASYN EAT!                ──────>     one audio buffer
```

### HPD1 — the one quality lever

`HPD1` carries a dictionary describing the screen we are mirroring onto:

```
Valeria                   bool   true      (the device name, historically)
HEVCDecoderSupports444    bool   true
DisplaySize               dict   Width / Height as float64 NSNumbers
```

**The phone renders to the size given here.** Asking for 1280x720 means 720p is
all the detail that exists, no matter how large the window is. `airplaya` passes
the configured resolution, which is why the app's screen-size picker matters on
the cable exactly as it does over Wi-Fi.

### HPA1 — the audio format

A dictionary whose `formats` key holds a 56-byte `AudioStreamBasicDescription`:
LPCM, 48000 Hz, 2 channels, 16-bit, 4 bytes per frame, format flags `12`
(signed integer, packed). The struct itself is 40 bytes; the phone expects the
sample rate repeated twice after it and ignores the packet without them.

`BufferAheadInterval` (0.073 s) and `ScreenLatency` (0.04 s) tell the phone how
far ahead to run. They are the values a Mac sends.

## 5. The media

### Video — ASYN FEED

```
asyn(4) clockRef(8) feed(4) sbuf...
```

An `sbuf` is a `CMSampleBuffer`, a block holding more blocks in no guaranteed
order:

| magic | contents |
|---|---|
| `opts` | output presentation timestamp, a `CMTime` |
| `stia` | timing info per sample: duration, presentation, decode |
| `sdat` | the encoded frame |
| `nsmp` | how many samples |
| `ssiz` | sample sizes |
| `fdsc` | a format description — dimensions, codec, parameter sets |
| `satt` | per-sample attachments |
| `sary` | a flag array |

`sdat` holds exactly what the Wi-Fi path holds after decryption: NAL units each
prefixed with a 4-byte big-endian length. So `to_annex_b` handles both, and
everything from there on — the decoder, the window, the clip recorder — is
shared code.

An `fdsc` turns up on the first frame and again whenever the stream changes
shape, which is what rotating the phone does. Its extensions hold a standard
**avcC** record two index-keyed dictionaries deep, under key 49 then key 105:

```
1  profile  compat  level  0xFF  0xE1  spsLen(2)  SPS  01  ppsLen(2)  PPS
```

Those are the SPS and PPS, prepended to the next frame as Annex-B so the
decoder can start there. A new `fdsc` with different parameter sets restarts the
sink, the same way new parameter sets do over Wi-Fi.

A buffer can carry an `fdsc` and no `sdat`: that is the phone announcing the
change before the frames that need it.

**The phone stops if you stop asking.** Every `FEED` is answered with an `ASYN
NEED`. Miss one and the stream stalls, which looks exactly like a decoder
problem and is not.

### Audio — ASYN EAT!

The same `sbuf`, with `sdat` holding interleaved 16-bit stereo PCM at 48 kHz.
Nothing to decode: it goes straight to the output device. Recording writes it to
a WAV at 48 kHz — the Wi-Fi path's 44.1 kHz header would play the clip back
slow.

The output presentation timestamp on each audio buffer is a reading of the
phone's audio clock, and together with our own reading at arrival it is what the
`SKEW` answer is computed from.

## 6. Shutting down

```
airplaya                            phone
  ASYN HPA0   ────>                 stop audio
  ASYN HPD0   ────>                 stop video
              <────   SYNC STOP     stop that clock
  RPLY        ────>
              <────   ASYN RELS     clock released (twice)
  ASYN HPD0   ────>
```

Then release the interface and put the configuration back. Skipping this leaves
the phone believing the session is still running, and it will refuse the next
one until it is unplugged.

## 7. Windows: the driver problem

This is why almost nothing offers wired iPhone mirroring on Windows, and why
`quicktime_video_hack`'s author wrote "I have given up on windows support".

**Windows does not let a user-mode program change a USB device's active
configuration.** The composite driver (`usbccgp`) picks the first configuration
at enumeration and owns that decision. WinUSB and libusbK both inherit the
limitation: they can talk to the interfaces of the *active* configuration and
nothing else. Since mirroring lives on configuration N, that is a dead end.

What works:

* **A libusb0-style filter driver** bound to the device. It sits *above* Apple's
  driver rather than replacing it — `usbmux` keeps working, iTunes keeps seeing
  the phone — and it permits vendor requests and non-first-configuration
  selection.
* **UsbDk**, which redirects the whole device to user mode. libusb's UsbDk
  backend implements `set_configuration` as a no-op, so the library call
  silently does nothing; `_select_configuration` notices by reading the active
  configuration back and falls through to a raw `SET_CONFIGURATION` request.

What does not work:

* Replacing Apple's driver with WinUSB via Zadig. It cannot switch
  configurations, and it breaks `usbmux` for everything else on the machine.

`airplaya` does not install anything. It reports what it found, and the desktop
app's preflight panel explains the prerequisite; installing a kernel driver is
not something a mirroring app should do behind your back.

macOS and Linux need none of this — libusb can select a configuration directly,
though on Linux the device needs a udev rule to be usable without `sudo`.

## 8. Symptom → cause

| What you see | What it usually is |
|---|---|
| "the phone did not expose its AV configuration" | the driver prerequisite, or an iPad in a state that needs a replug |
| "could not select the AV configuration" | WinUSB or libusbK is bound to the device |
| The link opens, then nothing arrives | no `NEED` was sent, or a halted endpoint that was not cleared |
| A few frames, then it stops | `NEED` is not being sent after every `FEED` |
| Video is fine, audio is silent | `HPA1` was rejected: the 56-byte format block is the usual reason |
| Audio drifts out of sync over minutes | `SKEW` is being answered with a constant |
| The picture is soft on a big window | `HPD1` asked for a small screen; the phone renders to what you ask for |
| Everything works once, then never until replug | the shutdown sequence did not run |
| `no backend available` | libusb is missing: `pip install libusb-package` |
